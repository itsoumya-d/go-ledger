Payments correctness, made inspectable.

A compact Go service for idempotent payment intents and double-entry ledger postings. The point is the invariants: replay-safe creation, capture-once under concurrency, postings that sum to zero, and a failed capture that leaves state untouched.

The invariants

01 / IDEMPOTENCY

Replay-safe creation

Same Idempotency-Key + same payload returns the original intent. Same key + different payload returns 409.

02 / DOUBLE ENTRY

Postings sum to zero

Capture writes a debit and a credit. The customer balance decreases; the merchant settlement balance increases by the same amount.

03 / CONCURRENCY

Capture exactly once

Ten concurrent captures produce exactly one posting pair. The second through tenth calls see “captured” and return the intent.

04 / FAILURE

Insufficient funds is a no-op

A failed capture leaves balances and postings untouched. The intent stays in requires_capture.

API in four calls

# fund an account (dev helper)
curl -s -X POST localhost:8080/v1/accounts/customer_a/fund \
  -H 'Content-Type: application/json' \
  -d '{"amount_cents":1000}'

# create an intent (idempotent)
curl -s -X POST localhost:8080/v1/payment_intents \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: order-42' \
  -d '{"account_id":"customer_a","amount_cents":400,"currency":"USD"}'

# capture
curl -s -X POST localhost:8080/v1/payment_intents/pi_1/capture

# balance
curl -s localhost:8080/v1/accounts/customer_a/balance

What this is not

Not production. The store is in-memory; state is lost on restart. No auth, no PCI scope, no real money. No persistence or FX. A production version needs the idempotency index and postings in one transactional store with a unique constraint on the key, plus a real ledger schema, reconciliation and settlement files. The interesting parts are CreateIntent, Capture, and the concurrency test — not the HTTP wrapper.
